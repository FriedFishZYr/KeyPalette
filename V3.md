# Keycap Colorizer — V3 Specification

## Overview

V3 builds directly on the V1 + V2 codebase. The theme is **visual fidelity and user experience**: the keyboard should start to *look* like real keycaps, stay centered and front-and-center while you work, and the selection/feedback model should be clear and unambiguous. It also adds side-by-side comparison.

No structural rewrites — additive features and targeted fixes only. All existing components, hooks, state shape, and data formats from V1/V2 remain in place unless explicitly noted as changed below.

This document is the authoritative build brief for V3. Work through features in the priority order listed. Each feature includes the exact files to touch and the precise behavior expected.

**No new dependencies.** Every V3 feature is pure SVG / CSS / in-browser color math. Do not add npm packages.

---

1. Prereq: color math utilities (`darken` / `lighten` / `mix` / `luminance` / `contrastText`)

10. Interop: persistence + JSON export bump to v3 (backward compatible)
11. Polish: comparison-mode PNG export, narrow-screen stacking
12. UX: collapsible toolbar sections (Presets, Profile, Legends, Export)

## 1. Prereq — Color Math Utilities

Profile shading, legend auto-contrast, and the selection halo all depend on color manipulation. Implement these in the existing `colorUtils.js` before anything else.

**Functions to add to `src/utils/colorUtils.js`:**

```js
export function luminance(hex) { ... }           // 0–1 relative luminance (WCAG-style)
export function lighten(hex, frac) { ... }        // mix toward #ffffff by frac (0–1)
export function darken(hex, frac) { ... }         // mix toward #000000 by frac (0–1)
export function mix(hexA, hexB, t) { ... }        // linear RGB mix, t = 0..1
export function shadeTowardContrast(hex, frac) {  // luminance-aware:
  // if hex is light (luminance > 0.5) → darken by frac
  // if hex is dark  → lighten by frac
}
export function contrastText(hex) { ... }         // "#000000" or "#ffffff", whichever reads better on hex
```

All operate on `#rrggbb` strings and return `#rrggbb`. Reuse the existing hex↔RGB helpers already in this file.

## 2. App Shell — Independent Scroll Regions

**Problem (observed):** The whole page scrolls as one unit. With many controls in the left panel, scrolling down to reach a feature also scrolls the keyboard out of view. The keyboard — the hero of the tool (per `PROPOSAL.md`) — should stay put while the controls scroll. This gets worse in V3, which adds several new panel sections (profile, legends, comparison controls, more presets, visual zone pills).

**Fix:** Restructure the app shell into fixed-height regions with independent scroll.
- Root app container: `height: 100vh; overflow: hidden;` as a flex row (toolbar | canvas) or grid.
- Toolbar / feature column: fixed width, `height: 100%`, `overflow-y: auto` — it scrolls on its own; the page never does.
- Keyboard canvas region: `flex: 1`, centered on both axes, no scroll of its own under normal conditions.

**Scale-to-fit (this is what makes the fixed center safe):** The canvas region measures its available width/height and scales the board (SVG `viewBox` fit, or a wrapper `transform: scale()`) so the full board always fits without clipping. **Cap the scale at 1** — shrink as needed, never enlarge beyond native. This is essential for the Full-size layout and for comparison mode (two boards), which can exceed the region.

**Fallbacks:**
- If content still can't fit at a reasonable minimum scale, let the canvas region itself scroll/pan (`overflow: auto` on that region) — the page-level scroll is never reintroduced.
- On narrow viewports, collapse to a stacked layout (toolbar above/below canvas) with normal page scroll — desktop-primary, same posture as V1/V2.
- Ensure no fixed `min-height` forces the canvas region to collapse to zero when the panel is tall.

**Files to touch:**
- `src/App.jsx` — shell structure (regions); measure the canvas region for scale-to-fit (a `ResizeObserver`, or a ref + window-resize listener)
- `src/App.module.css` — fixed-height shell, region overflow rules, responsive stacking
- `src/components/Toolbar/Toolbar.module.css` — column `overflow-y: auto`, full height
- `src/components/Keyboard/Keyboard.jsx` — apply the computed fit scale to the SVG

**No new state** — the fit scale is derived from container size and the current layout; it does not live in `useColorway`.

**Note:** Fixing the canvas region also stabilizes the hex badge (feature 4), whose absolute position is now relative to a non-scrolling container.

## 3. UX Fix — Selection & Press Feedback (Frame Indicator)

**Problem (observed):** Selecting or pressing a key currently changes its apparent fill — a faint white overlay / gloss. On WoB (white keycaps) the selection is nearly invisible; on colored keycaps it reads as a glossy color shift; and pressing a key briefly illuminates it, which looks like the key's color changed. Feedback is being expressed through the fill, so it competes with — and is confused for — the keycap's actual color.

**Fix:** Decouple state feedback from fill. The keycap fill must *only ever* show the key's true color.

- **Selected state → a frame ring.** Draw a stroke around the keycap's outer (footprint) rect: 2px in `--ws-accent`, plus a 1px contrasting halo (a second stroke derived from the workspace background) immediately outside it, so the ring stays visible over any keycap color and on either workspace theme. No fill change.
- **Hover state → a faint ring.** 1px, reduced-opacity version of the selection ring — visibly distinct from "selected."
- **Press feedback → geometric only.** A brief transform on click (e.g. scale to ~0.97 then back over 60–100ms, or a 1px downward translate). Preserves the V1 "soft key-press feedback" intent without any color/brightness change.
- **Multi-select** → every selected key shows the ring.

**Accent token:** add `--ws-accent` to both themes in `App.module.css`. Pick a hue with adequate contrast on both `#111111` (dark bg) and `#f0f0f0` (light bg) — e.g. `#4f8cff`. Define a per-theme variant only if one value can't satisfy both.

**Files to touch:**
- `src/components/Keyboard/KeyCap.jsx` — render selection/hover ring; apply press transform
- `src/components/Keyboard/Keyboard.jsx` — pass selection/hover state through
- `src/App.module.css` — `--ws-accent` token (both themes)
- `src/components/Keyboard/Keyboard.module.css` — press transform animation, ring styles

**Note:** The ring sits around the outer (sidewall) rect, so it behaves consistently once profile shading (feature 5) insets the top surface.

## 4. UX Fix — Hex Badge Clears on Outside Click

**Problem (observed):** The hex badge (V2 polish) stays visible after selecting a key; clicking empty space outside the keyboard does not dismiss it.

**Fix:** Clicking empty canvas space clears the current selection. Because the badge only renders when `selectedKeys.length === 1`, clearing the selection hides it automatically.

**Behavior:**
- A click on the SVG/canvas background (not on a key) → `clearSelection()` (sets `selectedKeys` to `[]`).
- Key clicks must `stopPropagation` so they don't bubble to the background handler and immediately deselect.
- Toolbar / panel clicks must not trigger deselection.
- `Escape` key also clears the selection.

**Files to touch:**
- `src/App.jsx` (or `src/components/Keyboard/Keyboard.jsx`) — background click handler + Escape listener
- `src/hooks/useColorway.js` — add `clearSelection()` if not already present

## 5. Feature — Keycap Profile Shading

**What it is:** A board-wide keycap profile selector — **Flat** (default), **SA**, **DSA**, **OEM**, **Cherry** — that changes how every keycap is shaded to simulate the profile's shape. Flat is the clean 2D keycap (V1/V2 look); the rest opt in to 3D shading. This is a *visual look*, not true geometry: we do not sculpt rows at different angles (deferred to a later version).

**Rendering model (per key, in `KeyCap.jsx`):** Replace the single rounded-rect fill with a layered render:

1. **Sidewall layer** — a rounded rect covering the full key footprint, filled with `shadeTowardContrast(keyColor, wallDarken)`. This is the visible body/walls of the cap and is what makes both light and dark keys read with depth.
2. **Top surface layer** — a smaller rounded rect, inset from the sidewall by `inset` on top/left/right and `inset + frontExtra` on the bottom (more sidewall shows at the front, simulating a slight downward viewing angle). Filled with `keyColor`.
3. **Dish overlay** — a gradient on the top surface to suggest the dish:
   - `dish: "cylindrical"` (OEM, Cherry) → vertical linear gradient, slightly lighter at top, darker at bottom (`±dishStrength`).
   - `dish: "spherical"` (SA, DSA) → radial gradient, lighter center → darker edges (`±dishStrength`).
4. **Top edge highlight** — a 1px stroke on the top edge of the top surface using `rgba(255,255,255,0.18)`.

The existing `--ws-key-border` 1px border (from V2) still applies to the outer sidewall rect.

**Profile definitions** — create `src/data/profiles.js` (mirrors the shape of `zones.js`). Starting values (tune visually during build):

```js
export const PROFILES = {
  // Flat is the default (clean 2D look). `flat: true` short-circuits the 3D
  // layered render in KeyCap; the others opt in to profile shading.
  flat:   { label: "Flat", flat: true },
  sa:     { label: "SA",     inset: 6, frontExtra: 5, dish: "spherical",   dishStrength: 0.14, wallDarken: 0.22 },
  oem:    { label: "OEM",    inset: 5, frontExtra: 4, dish: "cylindrical", dishStrength: 0.10, wallDarken: 0.18 },
  cherry: { label: "Cherry", inset: 4, frontExtra: 3, dish: "cylindrical", dishStrength: 0.08, wallDarken: 0.16 },
  dsa:    { label: "DSA",    inset: 3, frontExtra: 1, dish: "spherical",   dishStrength: 0.06, wallDarken: 0.10 },
};
```

(`inset` / `frontExtra` are in px at `UNIT = 54`; scale proportionally if `UNIT` ever changes.)

**Default profile:** `"flat"` — the clean 2D look ships by default; the 3D profiles are opt-in. (This overrides the original `"cherry"` default by product decision — flat is the safe, clean baseline, and the 3D shading is there for users who want realism.) Colorways saved before V3 (no `profile` field) load as `"flat"`.

**Flat render:** a single rounded rect in the true color (the V1/V2 keycap) — no sidewall/top-surface/dish/edge-highlight, and KeyCap declares no dish gradient for it.

**UI:** A "Profile" pill row in the Toolbar — five options (`Flat · SA · OEM · Cherry · DSA`), names only, visually quiet (matches the V2 zone/preset pills). A pill row is used over a segmented control so all five labels fit cleanly.

**Files to touch / create:**
- `src/data/profiles.js` — **NEW**: profile definitions above
- `src/components/Keyboard/KeyCap.jsx` — `flat` branch (single rect, V2 legend placement) vs. layered profile-aware render; 3D profiles center the legend on the top surface
- `src/components/Keyboard/Keyboard.jsx` — pass `profile` down; declare the dish gradient `<defs>` once (only for non-flat profiles), not per key
- `src/components/Toolbar/Toolbar.jsx` — add the Profile selector
- `src/hooks/useColorway.js` — add `profile` to state + `setProfile(id)` action

**Notes:**
- Spacebar and large keys use the same inset values — proportions still read correctly.
- True per-row SA sculpting is **out of scope** for V3.
- PNG export (V2) captures the DOM/SVG, so profile shading is included automatically.

## 6. Feature — Side-Legend Coloring (fixes invisible legends on dark caps)

**What it is:** Legends become independently colorable (double-shot / dye-sub simulation) and can sit on the top surface or the front sidewall. This also directly fixes the observed bug where **black legends are invisible on black/dark keycaps**.

**State additions (`useColorway.js`):**
```js
legendColor: "auto",       // "auto" | "#rrggbb"
legendPosition: "top",     // "top" | "front"
```

**Behavior:**
- `legendColor: "auto"` (**default**) → each legend uses `contrastText(keyColor)` per key, so it's always readable: white legends on dark caps, black on light caps. This resolves the dark-keycap visibility bug.
- `legendColor: "#rrggbb"` → all legends render in that exact color (the common real-world case: a set with one consistent legend color).
- `legendPosition: "top"` → legend centered on the top surface (3D profiles). In **flat** mode the legend keeps V2 placement (bottom-left, left-aligned) regardless of `legendPosition` — flat has no front band.
- `legendPosition: "front"` → legend rendered on the front sidewall strip exposed by the profile (the bottom `inset + frontExtra` band), smaller font, simulating front-printed legends. On DSA the band is shallow but still renders. Ignored in flat mode.

Auto-contrast applies in **flat** mode too — it's a legibility fix independent of profile shading, so even the clean 2D look gets readable legends on dark caps.

**UI:** A "Legends" section in the Toolbar:
- A native color swatch (`<input type="color">`, mirroring the existing Case-color control) plus an "Auto" toggle that returns `legendColor` to `"auto"`. *(Note: the codebase never actually implemented the V2 "unified picker context" — Case is a native input too — so retrofitting a context-switching mode into `ColorPanel` was rejected as a larger restructure than warranted. A native swatch gives the same outcome with less risk to V2 behavior.)*
- A two-option segmented toggle: "Top / Front" for `legendPosition`.

**Files to touch:**
- `src/components/Keyboard/KeyCap.jsx` — apply `legendColor` (resolving `"auto"` per key) and position per `legendPosition`
- `src/components/Toolbar/Toolbar.jsx` — Legends section UI (native swatch + Auto toggle + Top/Front segmented)
- `src/hooks/useColorway.js` — `legendColor`, `legendPosition` state + `setLegendColor` / `setLegendPosition` actions

**Out of scope for V3:** per-key or per-zone legend colors (V3 ships a single global legend color).

## 9. Feature — Comparison Mode

**What it is:** Two keyboards side by side, **same layout**, to compare two colorways. The primary board (**A**) is the live, fully-editable colorway. The comparison board (**B**) is a **read-only reference**.

**State additions (`useColorway.js`):**
```js
comparison: {
  active: false,
  board: null,   // snapshot: { name, layout, caseColor, caseFinish, profile,
                 //             legendColor, legendPosition, keyColors }
}
```

**Behavior:**
- A toggle in the Toolbar turns comparison mode on/off.
- When active, the "Set B from…" source controls appear inline in the Toolbar (not a modal); until B is chosen, `ComparisonView` shows an empty-state prompt on the right:
  - **Duplicate A** — snapshot A into B
  - **Load preset** — zone-based, layout-agnostic, always allowed (a dropdown)
  - **Load saved slot** — only slots whose `layout` matches A's current layout are enabled; others disabled with a "Different layout" title
- Both boards render side by side (A left, B right), same layout, each with its own case + profile + legends. The scale-to-fit shell (feature 2) splits the canvas region between them and keeps both visible.
- A muted label sits above each board: A shows `colorwayName`, B shows `board.name`.
- **All editing tools act on A only.** B is reference-only in V3 (read-only: no clicks, hover rings, selection, or hex badge).
- Controls: the inline source picker and "Clear B".

**Files to touch / create:**
- `src/components/ComparisonView/ComparisonView.jsx` — **NEW**: lays out A and B; renders B by passing the snapshot into the existing `Keyboard` via `data` + `readOnly`; splits `availableWidth`/`availableHeight` between the boards
- `src/components/ComparisonView/ComparisonView.module.css` — **NEW**
- `src/components/Keyboard/Keyboard.jsx` — accept optional `data` / `readOnly` / `boardId` props so it can render an arbitrary snapshot, not just live state (default path unchanged)
- `src/components/Keyboard/KeyCap.jsx` — `interactive` prop to suppress cursor/press/hover/click on the read-only board
- `src/components/Toolbar/Toolbar.jsx` — comparison toggle + inline "Set B from…" (Duplicate A / preset dropdown / matching slots) + "Clear B"
- `src/hooks/useColorway.js` — `toggleComparison()`, `setComparisonBoard(snapshot)`, `clearComparisonBoard()`, and snapshot builders `snapshotCurrent()` / `snapshotFromPreset(preset)` / `snapshotFromSlot(slot)`; `comparison` lives in component state (`useState`), not the persisted slot store
- `src/App.jsx` — render `ComparisonView` when `comparison.active`, else the single `Keyboard`; holds a second ref (`boardRefB`) for B and passes `slots` to the Toolbar

**Out of scope for V3 (fast-follow):** editable B, A↔B swap, cross-layout comparison.

## 10. Interop — Persistence & JSON Export

The new persistable fields (`profile`, `legendColor`, `legendPosition`) must round-trip through localStorage slots and JSON export/import. `colorHistory` (V2) keeps its own key; `comparison` is session-only and is **not** persisted.

**localStorage slot schema** — extend each slot object (`"keycap-colorizer-slots"`):
```js
{
  name, layout, caseColor, caseFinish, keyColors, savedAt,  // V1/V2
  profile: "flat",            // NEW (default flat)
  legendColor: "auto",        // NEW
  legendPosition: "top",      // NEW
}
```
On restore, any slot missing these fields gets the defaults above (backward compatible).

**JSON export** — bump `version` to `3`; add the three fields:
```js
{
  version: 3,
  name, layout, caseColor, caseFinish,
  profile: "flat",
  legendColor: "auto",
  legendPosition: "top",
  keyColors: { ... },
  exportedAt: "2026-..."
}
```

**JSON import validation** — accept `version` 1, 2, or 3:
- Missing `profile` → `"flat"`
- Missing `legendColor` → `"auto"`
- Missing `legendPosition` → `"top"`
- All other V2 validation rules (valid `layout`, non-null `keyColors`) still apply; same inline-error behavior (no `window.alert`).

**Files to touch:**
- `src/utils/exportJson.js` — `serializeColorway()` emits v3; `deserializeColorway()` default-fills the three fields for older (v1/v2) versions
- `src/hooks/useColorway.js` — `importColorway(data)` applies the new fields; the state derivation default-fills `profile`/`legendColor`/`legendPosition` on read, so pre-V3 slots load cleanly without changes to the generic `useLocalStorage.js` hook (`snapshotFromSlot` likewise default-fills)

## 12. UX — Collapsible Toolbar Sections

The longer Toolbar sections collapse behind a chevron header to keep the panel tidy — important now that there are 16 presets plus the added V3 controls (profile, legends, comparison). Applied to **Presets**, **Profile**, **Legends**, and **Export**; all default collapsed.

**Behavior:**
- Each header is a full-width toggle button (`aria-expanded`) with the section title, a chevron (`▸` collapsed / `▾` open), and — where there's a single meaningful active value — a muted summary so the current state reads at a glance while collapsed:

  - **Profile** → current profile label (`Flat`)
  - **Legends** → `color · position` (`Auto · top`)
  - **Export** → chevron only (no single value to summarize)
- UI-only `useState` per section — **not** persisted, and adds no `useColorway` state.
- One shared set of header styles (`sectionToggle` / `sectionMeta` / `sectionCount` / `sectionChevron`); `ExportPanel` keeps a small self-contained copy since it has its own stylesheet.

**Files to touch:**
- `src/components/Toolbar/Toolbar.jsx` + `Toolbar.module.css` — per-section toggle state + shared header styles (Presets, Profile, Legends)
- `src/components/ExportPanel/ExportPanel.jsx` + `ExportPanel.module.css` — Export toggle + self-contained header styles
